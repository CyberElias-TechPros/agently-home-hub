# Architecture

## Deployment topology

```
                    ┌─────────────────────────┐
   Browser ────────►│  Vercel (static + SPA)  │
                    └───────────┬─────────────┘
                                │ rewrite /api/* (same origin)
                                ▼
                    ┌─────────────────────────┐
                    │  Cloudflare Worker      │
                    │  Hono + Zod             │
                    └───┬────┬────┬────┬──────┘
                        │    │    │    │
            ┌───────────┘    │    │    └────────────┐
            ▼                ▼    ▼                 ▼
          D1 (SQL)      R2 (documents) KV (cache,   Queues
                                        rate limits) (notifications)
                                                     │
                                          Durable Object
                                          (realtime hub)
```

The frontend and API are separate deployables. The browser only ever knows one
origin: Vercel. `/api/*` is rewritten to the Worker, which keeps cookies and
CORS out of the picture entirely and means a misconfigured API URL cannot break
a production build.

## Why these services

| Service | Used for | Why |
| --- | --- | --- |
| **D1** | All relational data | Tenancies, maintenance and listings are relational and need joins and transactions across tables |
| **R2** | Uploaded documents | Object storage with no egress fee; documents are large and read rarely |
| **KV** | Response cache and rate limit counters | Eventually-consistent, globally replicated, single-digit-millisecond reads — correct for both uses |
| **Queues** | Notification delivery | Email and push are slow and retriable; they must not sit in the request path |
| **Durable Objects** | Realtime hub | Strongly consistent single instance per conversation; the only way to coordinate WebSockets at the edge |
| **Cron** | Housekeeping, saved-search digests | Nightly purge of abandoned uploads and expired tokens |

## API structure

`worker/src/` is layered so that each layer has one job:

```
routes/     HTTP concerns: parse, validate, authorise, respond
domain/     business rules: state machines, scoring, DTO mapping
services/   cross-cutting: notifications, matching, audit
repositories/  D1 access: SQL lives here and nowhere else
lib/        primitives: errors, crypto, JWT, logging
http/       middleware: request context, rate limiting, responses
```

Routes never write SQL and repositories never make authorisation decisions. A
route resolves the caller, asks a domain function whether the transition is
legal, and then asks a repository to persist it.

### Request lifecycle

1. `withRequestContext` assigns a request id and starts the timer.
2. `noStore` marks all responses private — nothing user-specific is cached.
3. Route-level `authenticate` / `optionalAuth` resolves the caller from the
   bearer token.
4. `requireAuth()` / `requireAnyRole()` enforce authorisation.
5. Validation happens with Zod **before** any database work.
6. The handler runs; success returns `{ data }`, failure throws `ApiError`.
7. `onError` maps every thrown error to a stable JSON envelope and logs it with
   the request id.

### Authorisation model

Roles are `tenant`, `landlord`, `agent`, `manager`, `admin`. Role checks gate
*entry* to a route, but never substitute for ownership checks: every endpoint
that touches a resource verifies the caller owns it, rents it, or manages it.
This is deliberate — a landlord role does not entitle you to someone else's
listing.

## Data model

24 tables, defined in `worker/migrations/0001_init.sql`. The consolidated
migration reconciles three defects inherited from the previous 17-migration
Postgres history:

1. `maintenance` and `maintenance_requests` both existed with different shapes.
2. `messages` was defined twice.
3. Several foreign keys were declared `INTEGER` while the referenced primary
   keys were UUID text.

Conventions:

- **IDs** — `TEXT` UUIDv4, generated by the application (`crypto.randomUUID()`)
  rather than the database, so an id can be known before the row is inserted.
- **Money** — `INTEGER` minor units (kobo). Every DTO divides by 100 on the way
  out, so **the API speaks naira and the database speaks kobo**.
- **Timestamps** — ISO 8601 UTC strings, written by the application so that
  local and remote behave identically.
- **Soft delete** — rows carry `deleted_at`; queries filter it out and the
  nightly cron purges.
- **Audit** — every admin action and security-relevant change is written to
  `audit_logs` with actor, action, resource and IP.

## Security model

| Concern | Approach |
| --- | --- |
| Passwords | PBKDF2-SHA256, 210 000 iterations, per-password salt stored with the hash |
| Password policy | Length (10–200) and a blocklist that sees through leet substitutions. No composition rules, per NIST SP 800-63B |
| Access tokens | HS256 JWT, 15 minutes, with issuer and audience claims verified on every request |
| Refresh tokens | 30 days, hashed at rest, rotated on every use; reuse of a spent token revokes the whole family |
| Account lockout | Progressive delay after repeated failures, per account |
| Rate limiting | KV sliding window, keyed by account and IP. Budgets are deliberately generous to accommodate carrier-grade NAT, which is the norm on Nigerian mobile networks |
| Enumeration | Registration responds identically whether or not an address exists; login errors do not distinguish "no such user" from "wrong password" |
| Object access | Document keys are owner-scoped and unguessable; downloads are authorised and served through short-lived signed URLs |
| Transport | Strict security headers, an explicit CORS allowlist, and `no-store` on every response |
| Secrets | Server-side only. Nothing prefixed `VITE_` is a secret, because `VITE_*` is inlined into the public bundle |

## Frontend

- **Routing** — React Router, every route except the landing page lazily loaded.
- **Data** — TanStack Query, with keys centralised in `src/lib/query-keys.ts` so
  invalidation is consistent.
- **Forms** — react-hook-form with Zod resolvers; the schema mirrors the API's
  so the client never accepts something the server will reject.
- **State** — authentication state lives in one provider; the API client owns
  token storage, so React and the network layer cannot disagree about whether
  you are signed in.
- **SEO** — a `useSEO` hook owns the document head (title, description,
  canonical, Open Graph) and `<JsonLd />` emits structured data that is removed
  on unmount. Authenticated routes are `noindex`.

### Known trade-offs

- Messaging polls every 10 seconds instead of holding a WebSocket. The Durable
  Object endpoint exists; wiring the browser to it would be the next step.
- There is no server-side rendering, so crawlers see the app shell. Structured
  data and accurate per-route metadata mitigate this, but a pre-rendering layer
  would be the robust fix for a content-heavy site.
- The property sitemap lists static routes only. Listing URLs live in the
  database; generating them at build time would require the API to be reachable
  from the build step.
